# 性能、安全与最小验收基线

> 状态：Draft v0.1  
> 日期：2026-07-26

## 1. 容量目标

第一阶段按以下容量设计：

| 指标 | 目标 |
| --- | --- |
| 注册用户 | 100,000 |
| 日活用户 | 10,000 |
| 常规峰值 | 500 RPS |
| 可横向扩展目标 | 2,000 RPS |
| 单用户 Experience | 200 |
| 单用户 Resume | 100 |
| 同步单页 | 最多 500 changes |

性能目标必须在明确的服务器、数据库规格和代表性数据量下验收。

## 2. 延迟目标

| 操作 | 目标 |
| --- | --- |
| 单记录读取 | p95 < 100ms |
| 普通列表 | p95 < 200ms |
| 普通写入 | p95 < 250ms |
| 同步 Push/Pull | p95 < 500ms |
| 错误率 | < 0.1%（不含用户输入错误） |
| 月可用性 | 99.9% |

可选 Resume 派生文件上传时间不计入普通 API 延迟；签名 URL 获取和 complete 校验需要
单独衡量。APP Material 没有云端上传链路。

## 3. 性能设计要求

### API

- 无状态实例；
- 设置请求体和响应体大小上限；
- 设置 Header、Read、Write、Idle timeout；
- 限制每实例并发和数据库连接；
- 使用流式 JSON 只限必要的大响应；
- 禁止无边界 goroutine；
- 优雅关闭；
- 热路径避免反射型重框架。

### PostgreSQL

- 所有列表使用 keyset cursor；
- 每个查询有确定索引；
- 禁止 N+1；
- 批量同步使用批量 SQL；
- 事务尽量短；
- 外部网络调用不放数据库事务内；
- 状态流转只锁定目标行；
- 持续监控慢查询和锁等待；
- 生产启用连接池容量预算；
- 表膨胀、VACUUM 和索引增长纳入监控。

### Redis

- 不缓存未经测量的普通 CRUD；
- 缓存 key 必须有 TTL 和用户隔离；
- 缓存失效不能造成越权；
- Redis 故障不能破坏数据库正确性。

## 4. 压测门禁

至少覆盖：

1. 10 万用户分布的代表性数据库；
2. Resume JSONB 大小的真实分布；
3. Application 看板混合查询；
4. 80% 读、20% 写混合流量；
5. 多设备同步 Push/Pull；
6. 热点用户和普通用户混合；
7. 数据库连接池耗尽；
8. Redis 不可用；
9. 单 API 实例下线；
10. 幂等重试和版本冲突。

报告必须包含：

- RPS；
- p50/p95/p99；
- 错误分类；
- CPU、内存和 goroutine；
- DB CPU、连接、锁和慢查询；
- 执行计划；
- 瓶颈和调优前后对比。

## 5. 安全基线

### 身份与会话

- 邮箱验证码防爆破和频率限制；
- Access Token 短有效期；
- opaque Session Token 只保存哈希并支持撤销；
- 设备级 Session；
- Renderer 不获取 Session Token；
- 生产禁止开发密码登录；
- 管理接口与用户 API 分离。

### 用户隔离

- 所有业务表带 `user_id`；
- Repository 方法必须要求 user ID；
- 任何关联写入都验证两端属于同一用户；
- 不相信客户端提交的 owner ID；
- 下载 URL 生成前重新校验权属；
- 越权测试作为每个资源的固定测试矩阵。

### 数据与日志

- 全链路 TLS；
- 数据库和对象存储静态加密；
- Token、验证码、邮箱正文和简历正文不写普通日志；
- 邮箱和 IP 在安全日志中脱敏或哈希；
- 错误响应不暴露内部栈；
- 备份恢复定期演练；
- 密钥不进入 Git 或 Docker 镜像。

### 文件

- APP Material 不得上传云端；
- 校验扩展名、MIME、大小和 SHA-256；
- 可选 Resume 派生文件上传状态未 complete 前不可关联；
- 文件名不直接成为 object key；
- 下载 URL 短时有效；
- 删除采用延迟回收；
- 后续增加恶意文件扫描 Adapter。

## 6. 最小验收

本项目不设置覆盖率指标，也不以测试文件数量作为完成门槛。开发时可以直接推进业务，但以下
结果必须能被实际证明：

- Docker 环境可启动，空库 Migration 可执行；
- 邮箱登录和开发登录在各自环境可用；
- APP 可完成 Experience、JD、Resume、Application 主流程；
- 用户 A 无法读取或修改用户 B 的数据；
- Resume 过期版本不会静默覆盖；
- Application 非法状态跳转会被拒绝；
- 同一 operation 重试不会重复创建；
- Pull 分页和删除墓碑不会让设备永久丢数据；
- 登出能撤销 Session；
- 代表性负载下达到本文性能目标。

实现者可选择自动化测试、一次性验证脚本或联调记录，但关键失败路径和性能指标必须留下可复核
证据。

## 7. 可观测性

每个请求记录：

- request ID；
- route template；
- status code；
- duration；
- user ID 的不可逆标识；
- device ID 的不可逆标识；
- DB query count；
- trace ID。

核心指标：

- API RPS、p95、p99；
- 5xx、409、422、429；
- 登录和验证码成功率；
- DB pool 使用率；
- 慢查询和锁等待；
- Sync backlog 和失败率；
- 对象上传 complete 失败率。

告警至少包括：

- 5xx 持续升高；
- p95 超目标；
- DB 连接接近上限；
- Replica/backup 异常；
- Sync backlog 持续增长；
- 邮件验证码发送异常；
- 磁盘或对象存储异常。

## 8. 发布门禁

生产发布前必须：

- 所有 Migration 在空库和上一版本库验证；
- 关键安全边界验证通过；
- 基准压测无性能回归；
- OpenAPI 的 APP 影响已评审；
- 镜像扫描通过；
- staging APP 四大业务闭环通过；
- 数据库备份和回滚步骤明确；
- 开发登录在生产配置下无法启用。
